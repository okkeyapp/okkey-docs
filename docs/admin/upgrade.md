# Обновление

Обновление одинаково на тарифе «Бесплатный» и на тарифе «Предприятие». Вы закрепляете новый тег образов, скачиваете подписанные образы и снова запускаете стек.

Файл `~/okkey/.env` и тома Docker сохраняйте. Повторный запуск установщика не меняет `OKKEY_IMAGE_TAG` в уже существующем `.env`. Тег правьте сами.

Команды ниже — для каталога `~/okkey` и проекта `okkey`. Другой каталог: перейдите в него и подставьте имя каталога в нижнем регистре в `-p`.

## Шаги

1. Снимите копию базы, тома MinIO и файла `.env`. См. [Копирование и восстановление](./backup-restore.md).
2. В `~/okkey/.env` запишите `OKKEY_IMAGE_TAG=<tag>`.
3. Обновите файл Compose с git-тега `v<tag>`, затем скачайте образы.

```bash
cd ~/okkey
curl -fsSL -o docker-compose.prod.yml \
  "https://raw.githubusercontent.com/okkeyapp/okkey/v<tag>/deploy/docker/docker-compose.prod.yml"
docker compose -p okkey -f docker-compose.prod.yml --env-file .env pull
```

Проверьте `api`, `worker` и `web` командой cosign из раздела [Версии и релизы](#версии-и-релизы). Затем запустите:

```bash
docker compose -p okkey -f docker-compose.prod.yml --env-file .env up -d
```

На этой машине откройте `http://127.0.0.1:4000/health`.

`OKKEY_RESET_VOLUMES=1` удаляет данные Postgres, Redis и MinIO. При обновлении его не задавайте.

Для релиза, на котором сейчас закреплены команды установки, `<tag>` — это `1.0.0-beta.2`, а git-тег — `v1.0.0-beta.2`.

## Что API делает при старте

API и воркер при старте применяют SQL-файлы из `services/api/migrations` по порядку и записывают имя файла в таблицу `schema_migrations`. Два процесса берут один и тот же блокировочный замок Postgres, поэтому одновременный старт не применяет один файл дважды.

База, созданная ещё v1.0.0-beta.1, таблицы `schema_migrations` не имеет: тот релиз накатывал файлы `0001`–`0034` через `psql`. При первом старте с мигратором API узнаёт такую схему и помечает `0001`–`0034` уже применёнными, а выполняет только файлы после `0034`. Все файлы подряд он не помечает. База, которая ни на одну известную отметку не похожа, не обновляется: процесс отказывается пропускать SQL.

Отдельных скриптов, которые снимают уже записанную миграцию, в этом запуске нет. Поэтому перед обновлением нужна [копия](./backup-restore.md). Возврат к старым данным описан на странице [Откат](./rollback.md).

## Окно в интерфейсе

Владелец может увидеть «Доступно обновление» и окно «Обновление системы». Текст окна: «Проверьте, что изменится. Установка начнётся только после нажатия «Обновить».» В окне строки «Okkey» и «Enterprise». Кнопки: «Обновить», «Пропустить», «Закрыть».

Если лента не задана, окно пишет: «Лента обновлений не задана. Можно применить файл пакета.» Подпись файла: «Офлайн-пакет». Пакет без подписи или с недействительной подписью не применяется. Если применение не удалось, текст говорит, что экземпляр остался на прежней версии.

Путь через тег образа выше — тот, что описан для Docker Compose. Окно не заменяет копию базы перед сменой версии.

## Версии и релизы {#версии-и-релизы}

Okkey нумерует версии по SemVer: `X.Y.Z`. Предрелизы помечаются суффиксом, например `1.0.0-beta.2` или `1.0.0-rc.1`.

| Что публикуется | Какие теги образов |
| --- | --- |
| Git-тег `vX.Y.Z` без суффикса | `:X.Y.Z`, `:X.Y` и `:X` |
| Git-тег предрелиза, например `v1.0.0-beta.2` | только `:1.0.0-beta.2` |

Установка закрепляет и git-ref, и тег образа. Для текущего текста команд это `OKKEY_REF=v1.0.0-beta.2` и `OKKEY_IMAGE_TAG=1.0.0-beta.2`. Плавающий тег `latest` в установке не используется.

Образы: `ghcr.io/okkeyapp/api`, `ghcr.io/okkeyapp/web`, `ghcr.io/okkeyapp/worker`. Их можно скачать без входа в реестр.

Проверка подписи после `docker compose pull`. Подставьте свой тег вместо `1.0.0-beta.2`:

```bash
digest="$(docker image inspect --format '{{index .RepoDigests 0}}' ghcr.io/okkeyapp/api:1.0.0-beta.2)"
cosign verify \
  --certificate-identity-regexp 'https://github.com/okkeyapp/okkey/\.github/workflows/publish-images\.yml@refs/(heads/dev|tags/v.+)' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "$digest"
```

Повторите для `worker` и `web`. Postgres, Redis и MinIO этой подписью не покрыты.

Заметки к релизу лежат на странице релизов GitHub: [github.com/okkeyapp/okkey/releases](https://github.com/okkeyapp/okkey/releases). У предрелиза в заметках есть отметка, что это ещё не финальная версия.

## Как проверить

```bash
cd ~/okkey
docker compose -p okkey -f docker-compose.prod.yml --env-file .env ps
curl -fsS http://127.0.0.1:4000/health
```

Сервисы `api`, `web` и `worker` запущены, у `api` состояние healthy. В ответе `/health` есть `"status": "ok"`. Откройте веб и войдите.

## Частые ошибки

| Что видно | Что сделать |
| --- | --- |
| `docker compose pull` не находит тег | Тега ещё нет в GHCR. Оставьте прежний `OKKEY_IMAGE_TAG` и прежний файл Compose. |
| `cosign verify failed` | Образ не совпал с подписью. Не запускайте его. Верните прежний тег из копии `.env`. |
| `password authentication failed for user "okkey"` | `POSTGRES_PASSWORD` не от этого тома. Верните `.env` из копии. |
| Установщик пишет, что тег в `.env` не изменён | Так и должно быть, если `.env` уже есть. Тег правьте в файле сами. |
| В `.env` случайно оказался `OKKEY_RESET_VOLUMES=1` | Уберите переменную до `up`. Иначе сотрутся база, Redis и MinIO. |
