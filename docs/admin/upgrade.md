# Обновление

Обновление одинаково на тарифе «Бесплатный» и на тарифе «Предприятие». Для Okkey (ядра) есть окно «Обновление системы», офлайн-пакет и ручная смена тега в Docker Compose. Для модуля Enterprise в этом выпуске основной путь - Compose по инструкции ниже.

Файл `~/okkey/.env` и тома Docker сохраняйте. Повторный запуск установщика не меняет `OKKEY_IMAGE_TAG` в уже существующем `.env`. Тег правьте сами.

Команды ниже - для каталога `~/okkey` и проекта `okkey`. Другой каталог: перейдите в него и подставьте имя каталога в нижнем регистре в `-p`.

## Ленты обновлений {#ленты-обновлений}

**Okkey (ядро).** Лента публикуется в GitHub Releases публичного репозитория [okkeyapp/okkey](https://github.com/okkeyapp/okkey/releases). В публичном релизе лежат `feed.json` и пакет `okkey-<version>.okpkg`. По умолчанию окно читает `https://github.com/okkeyapp/okkey/releases/latest/download/feed.json`. Пустой `OKKEY_UPDATE_CORE_FEED_URL` как раз значит эту ленту. Старое имя той же настройки - `OKKEY_UPDATE_FEED_URL`.

**Enterprise.** Отдельная онлайн-лента Enterprise появится в следующем выпуске и потребует ключа лицензии. В этом выпуске модули Enterprise включают через `ENTERPRISE_MODULES`. Ключ лицензии для модулей сейчас не нужен. Обновление Enterprise сейчас - через [Compose](#шаги) или офлайн-пакет, который выдаётся клиентам Enterprise вместе с релизом Enterprise.

В окне «Обновление системы» строка называется «Okkey». Строка «Enterprise» появляется, когда модуль установлен. Как устроен экран - в разделе [Окно в интерфейсе](#окно-в-интерфейсе).

## Шаги через Docker Compose {#шаги}

### Okkey (ядро)

1. Снимите копию базы, тома MinIO и файла `.env`. См. [Копирование и восстановление](./backup-restore.md).
2. В `~/okkey/.env` запишите `OKKEY_IMAGE_TAG=<tag>`.
3. Обновите файл Compose с git-тега `v<tag>`, затем скачайте образы.

```bash
cd ~/okkey
curl -fsSL -o docker-compose.prod.yml \
  "https://raw.githubusercontent.com/okkeyapp/okkey/v<tag>/deploy/docker/docker-compose.prod.yml"
docker compose -p okkey -f docker-compose.prod.yml --env-file .env pull
```

Проверьте `api`, `worker` и `web` командой cosign из раздела [Версии и релизы](#версии-и-релизы). Затем запустите:

```bash
docker compose -p okkey -f docker-compose.prod.yml --env-file .env up -d
```

На этой машине откройте `http://127.0.0.1:4000/health`.

`OKKEY_RESET_VOLUMES=1` удаляет данные Postgres, Redis и MinIO. При обновлении его не задавайте.

Для релиза, на котором сейчас закреплены команды установки, `<tag>` - это `1.0.0-beta.3`, а git-тег - `v1.0.0-beta.3`.

### Enterprise

В этом выпуске основной путь обновления Enterprise - Docker Compose.

Публичный `docker-compose.prod.yml` из okkey держит те же сервисы `api`, `web`, `worker` и `update-agent`. Модуль Enterprise подменяет образы `api`, `web` и `worker` через `OKKEY_API_IMAGE`, `OKKEY_WEB_IMAGE` и `OKKEY_WORKER_IMAGE`. Сервис `update-agent` тоже берёт образ из `OKKEY_API_IMAGE`. Тег берётся из `OKKEY_ENTERPRISE_IMAGE_TAG`, а если он пуст - из `OKKEY_IMAGE_TAG`. Имена `enterprise-api`, `enterprise-web` и `enterprise-worker` встречаются только как ключи внутри офлайн-пакета Enterprise; отдельных сервисов Compose с такими именами нет.

Когда модуль уже установлен:

1. Снимите [копию](./backup-restore.md).
2. В `.env` запишите новый `OKKEY_ENTERPRISE_IMAGE_TAG` и при необходимости имена образов, которые оставил сотрудник Okkey при подключении тарифа (`OKKEY_API_IMAGE`, `OKKEY_WEB_IMAGE`, `OKKEY_WORKER_IMAGE`).
3. Обновите файл Compose с git-тега `v<tag>`, скачайте образы, проверьте подпись cosign, затем перезапустите стек:

```bash
cd ~/okkey
curl -fsSL -o docker-compose.prod.yml \
  "https://raw.githubusercontent.com/okkeyapp/okkey/v<tag>/deploy/docker/docker-compose.prod.yml"
docker compose -p okkey -f docker-compose.prod.yml --env-file .env pull
```

Проверьте образы Enterprise подписью cosign командой из раздела [Версии и релизы](#версии-и-релизы). Затем запустите:

```bash
docker compose -p okkey -f docker-compose.prod.yml --env-file .env up -d
```

Пакет или образ Enterprise требует достаточно новую версию Okkey. Сначала обновите ядро, если установка об этом пишет.

## Что API делает при старте

API и воркер при старте применяют SQL-файлы из `services/api/migrations` по порядку и записывают имя файла в таблицу `schema_migrations`. Два процесса берут один и тот же блокировочный замок Postgres, поэтому одновременный старт не применяет один файл дважды.

База, созданная ещё v1.0.0-beta.1, таблицы `schema_migrations` не имеет: тот релиз накатывал файлы `0001`-`0034` через `psql`. При первом старте с мигратором API узнаёт такую схему и помечает `0001`-`0034` уже применёнными, а выполняет только файлы после `0034`. Все файлы подряд он не помечает. База, которая ни на одну известную отметку не похожа, не обновляется: процесс отказывается пропускать SQL.

Отдельных скриптов, которые снимают уже записанную миграцию, в этом запуске нет. Поэтому перед обновлением нужна [копия](./backup-restore.md). Возврат к старым данным описан на странице [Откат](./rollback.md).

## Окно в интерфейсе {#окно-в-интерфейсе}

Окно есть только на self-hosted, на тарифе «Бесплатный» и на тарифе «Предприятие». Его видит любой вошедший. Внизу сайдбара написана версия, например `v1.0.0-beta.3`. Если сервер знает коммит, из которого собрано ядро, в скобках добавляются первые 8 символов его SHA: `v1.0.0-beta.3 (2bf668f3)`. Полный SHA лежит в атрибуте `data-commit-sha`. Когда версия - это сам SHA коммита, в сайдбаре показывается `v0.0.0-dev` и короткий SHA в скобках, например `v0.0.0-dev (2bf668f3)`. Адрес окна: `?popup=systemUpdate`.

Пока в ленте есть версия новее той, которую уже открывали в этом окне, значок версии другой. Для чтения с экрана рядом звучит «Доступно обновление». В свёрнутом сайдбаре виден значок, текст версии скрыт. Открытие окна снимает это состояние для показанных версий.

Заголовок окна: «Обновление системы». Текст: «Проверьте онлайн-обновления из ленты или загрузите офлайн-пакет - он применится после успешной проверки.» «Закрыть» не нажимается, пока обновление идёт.

Окно разделено на онлайн-обновление и загрузку офлайн-пакета. Офлайн-пакет после успешной локальной проверки применяется автоматически. В строках окна «Okkey» и, если модуль установлен, «Enterprise» показаны текущая версия и, когда установка сообщает коммит, короткий SHA в скобках, например `1.0.0-beta.3 (6e6ee86)`.

Для Okkey в этом выпуске окно подходит и для онлайн-ленты ядра, и для офлайн-пакета ядра. Для Enterprise основной путь обновления - [Compose](#шаги).

### Онлайн-обновление

Блок называется «Онлайн-обновление».

Если проверка по сети выключена (`OKKEY_UPDATE_ISOLATED=true`), вместо строк написано: «Онлайн-обновление отключено администратором сервера. Воспользуйтесь офлайн-пакетом ниже.» Подробнее - в разделе [Изолированный режим](#изолированный-режим).

Иначе окно показывает строку «Okkey». Строка «Enterprise» есть, когда модуль Enterprise установлен: в ней видны текущая версия и короткий SHA, когда установка его сообщает. Онлайн-лента Enterprise появится в следующем выпуске.

Для Okkey в строке «Текущая версия {'{version}'}». Если API знает коммит, к версии добавляется короткий SHA. Если в ленте ядра есть новее, рядом «Новая версия {'{version}'}», краткий текст выпуска и ссылка «Примечания к выпуску», когда у выпуска есть адрес `http` или `https`. Если новее нет: «Актуальная версия». Если ленту ядра прочитать не удалось: «Не удалось проверить Okkey.»

Пустой список при настроенной ленте ядра: «Эта установка уже на актуальной версии.» Если ленты нет: «Лента обновлений не задана. Ниже можно загрузить офлайн-пакет.» Непрочитанная лента: «Не удалось прочитать ленту обновлений. Ничего не применено.»

Как задаётся лента ядра - в разделе [Ленты обновлений](#ленты-обновлений).

Применить обновление из ленты ядра может только владелец пространства. У остальных: «Применить обновление может только владелец пространства.» Кнопок «Обновить» у них нет.

У владельца, когда в ленте ядра есть что ставить, справа «Пропустить» и «Обновить». У строки Okkey своя кнопка «Обновить Okkey».

«Пропустить» прячет эти версии, пока в ленте не появится более новая. У владельца скрытие общее для установки. У остальных оно остаётся в этом браузере.

Пока пакет качается: «Скачиваем пакет…». Затем «Проверяем подпись пакета…» и «Применяем обновление…». Итог:

- Только Okkey: «Обновление применено. Okkey перезапускается на {'{version}'}.»
- Только Enterprise: «Обновление применено. Enterprise {'{version}'} установлен.»
- Оба: «Okkey {'{core}'} и Enterprise {'{enterprise}'} применены.»
- Частичный пакет (Okkey применён, Enterprise нет): «Okkey {'{core}'} применён, Enterprise остался на прежней версии. Повторите обновление Enterprise.» Под ним: «Okkey применён. Enterprise не применён и откачен.» Кнопка «Повторить обновление Enterprise».
- Полный сбой: «Обновление не применено. Экземпляр остался на прежней версии.»

Под сообщением о сбое бывает то же или более точный текст:

| Что видно | Что это значит |
| --- | --- |
| «У пакета нет подписи, поэтому он не применён.» | Подписи в пакете нет. |
| «Подпись пакета недействительна, поэтому он не применён.» | Подпись не сошлась. |
| «Проверка подписи прервана, поэтому пакет не применён.» | Проверка оборвалась. |
| «Не задан доверенный открытый ключ, поэтому пакет не применён.» | В `.env` нет ключа, которым окно проверяет пакет. Для Okkey это `OKKEY_UPDATE_TRUSTED_PUBLIC_KEY`, для Enterprise - `OKKEY_UPDATE_ENTERPRISE_TRUSTED_PUBLIC_KEY`. |
| «Агент обновлений недоступен. Ничего не применено.» | Сервис, который ставит пакет, не ответил. |
| «Подпись пакета Enterprise проверена, но эта установка не может применить модуль Enterprise. Okkey не изменён.» | Пакет Enterprise на этой установке некуда ставить. |
| «Сначала обновите ядро. Этому пакету Enterprise нужна более новая версия ядра, поэтому ничего не изменено.» | Пакет Enterprise новее, чем установленный Okkey. |
| «Okkey применён. Enterprise не применён и откачен.» | Общий архив поставил Okkey, а Enterprise откатился. |
| «Срок лицензии Enterprise истёк.» | Лицензия Enterprise истекла. |
| «Офлайн-пакет больше допустимого размера.» | Пакет, в котором zip-архив больше 1 000 000 байт. |
| «Обновление не применено. Экземпляр остался на прежней версии.» | Применение оборвалось. |

Путь через тег образа выше - тот, что описан для Docker Compose. Окно не заменяет копию базы перед сменой версии.

### Офлайн-пакет

Блок называется «Офлайн-пакет». Текст: «Загрузите подписанный пакет (.okpkg / .json с payload+signature) или общий архив (.okbundle, .zip). После успешной локальной проверки пакет применяется автоматически.» Кнопка «Загрузить офлайн-пакет». Можно выбрать несколько файлов. У выбранного файла кнопка «Удалить файл».

После успешной локальной проверки пакет применяется автоматически. Это и подписанный файл (`.okpkg` / `.json`), и общий архив (`.okbundle`, `.zip`). Второй кнопки «Обновить» для этого нет. Пакет, в котором zip-архив больше 1 000 000 байт: «Офлайн-пакет больше допустимого размера.» Чужой файл: «Файл не является офлайн-пакетом Okkey.» Распознанный файл, из которого сейчас нечего ставить: «Пакет распознан, но сейчас из него нечего применять.»

Тот, кто не владелец, при выборе файла видит: «Применить обновление может только владелец пространства.» Кнопка загрузки у него выключена.

Пакет ядра `okkey-<version>.okpkg` берите с [публичных релизов okkey](https://github.com/okkeyapp/okkey/releases). Общий архив `.okbundle` в публичные Releases okkey не входит: его выдают клиентам Enterprise вместе с релизом Enterprise. Для обновления Enterprise в этом выпуске основной путь - [Compose](#шаги).

## Изолированный режим {#изолированный-режим}

`OKKEY_UPDATE_ISOLATED=true` отключает онлайн-проверки, в том числе ленту ядра по умолчанию. Обновление тогда - через офлайн-пакет или Compose.

### Что скачать

- Только Okkey: с [страницы релизов okkey](https://github.com/okkeyapp/okkey/releases) файл `okkey-<version>.okpkg` для нужного тега. Рядом в публичном релизе лежит `feed.json`. Общего архива `.okbundle` в публичных Releases okkey нет.
- Okkey и Enterprise вместе: общий архив `.okbundle` выдаётся клиентам Enterprise вместе с релизом Enterprise. Рядом может быть файл контрольной суммы `.sha256`. В архиве оба пакета.

Окно также принимает общий архив в виде `.zip` с теми же пакетами.

### Как проверить

Если вместе с общим архивом выдали файл `.sha256`, сверьте контрольную сумму:

```bash
echo "$(cat okkey-offline-<version>.okbundle.sha256)  okkey-offline-<version>.okbundle" | sha256sum -c -
```

Либо сравните хеш скачанного файла с одной строкой в `.sha256`. После загрузки окно ещё раз проверяет подпись пакета доверенными ключами из `.env`. Для пакета ядра достаточно `OKKEY_UPDATE_TRUSTED_PUBLIC_KEY`. Для пакета Enterprise и для общего архива `.okbundle` нужен ещё `OKKEY_UPDATE_ENTERPRISE_TRUSTED_PUBLIC_KEY`. Без нужного ключа пакет не применяется.

В изолированном режиме образы из сети не скачиваются. Нужные образы должны уже быть на машине, иначе применение остановится.

### Как загрузить

1. Откройте окно «Обновление системы» из версии в сайдбаре.
2. В блоке «Офлайн-пакет» нажмите «Загрузить офлайн-пакет» и выберите файл пакета `.okbundle` (в нём и ядро, и Enterprise) или отдельный `.okpkg`.
3. После успешной локальной проверки пакет применяется автоматически. Второй кнопки «Обновить» нет.

Применить может только владелец пространства. Сначала снимите [копию](./backup-restore.md). Для Enterprise в изолированной установке используйте [Compose](#шаги) и пакеты, выданные вместе с релизом Enterprise.

## Версии и релизы {#версии-и-релизы}

Okkey нумерует версии по SemVer: `X.Y.Z`. Предрелизы помечаются суффиксом, например `1.0.0-beta.3` или `1.0.0-rc.1`.

| Что публикуется | Какие теги образов |
| --- | --- |
| Git-тег `vX.Y.Z` без суффикса | `:X.Y.Z`, `:X.Y` и `:X` |
| Git-тег предрелиза, например `v1.0.0-beta.3` | только `:1.0.0-beta.3` |

Установка закрепляет и git-ref, и тег образа. Для текущего текста команд это `OKKEY_REF=v1.0.0-beta.3` и `OKKEY_IMAGE_TAG=1.0.0-beta.3`. Плавающий тег `latest` в установке не используется.

Образы Okkey: `ghcr.io/okkeyapp/api`, `ghcr.io/okkeyapp/web`, `ghcr.io/okkeyapp/worker`. Их можно скачать без входа в реестр.

В публичных Releases okkey публикуются `feed.json` и `okkey-<version>.okpkg`. Общий архив `.okbundle` туда не входит.

`docker compose pull` подпись образов не проверяет. Установщик `install.sh` после `pull` и до `up` проверяет её сам. При ручном обновлении cosign запускает администратор.

Команда ниже проверяет только образы ядра (`ghcr.io/okkeyapp/api`, `web`, `worker`). Подставьте свой тег вместо `1.0.0-beta.3`:

```bash
digest="$(docker image inspect --format '{{index .RepoDigests 0}}' ghcr.io/okkeyapp/api:1.0.0-beta.3)"
cosign verify \
  --certificate-identity-regexp '^https://github\.com/okkeyapp/okkey/\.github/workflows/publish-images\.yml@refs/(?:heads/dev|tags/v[0-9]+\.[0-9]+\.[0-9]+(?:-[0-9A-Za-z-]+(?:\.[0-9A-Za-z-]+)*)?)$' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "$digest"
```

Повторите для `worker` и `web`. Postgres, Redis и MinIO этой подписью не покрыты.

Образы Enterprise - `ghcr.io/okkeyapp/okkey-enterprise/api`, `ghcr.io/okkeyapp/okkey-enterprise/worker` и `ghcr.io/okkeyapp/okkey-enterprise/web`. Их подписывает репозиторий `okkey-enterprise` (процесс GitHub Actions `publish-images.yml`, тот же издатель OIDC `https://token.actions.githubusercontent.com`). Доверенные теги и ветки - теги релиза `v*`, ветки `release/*` и `hotfix/*` (не `dev`). Для проверки нужен идентификатор подписи этого репозитория, а не команда ядра выше. Образы закрытые: перед `pull` и проверкой выполните `docker login ghcr.io`. Подставьте свой тег в `OKKEY_ENTERPRISE_IMAGE_TAG`:

```bash
identity_regexp='^https://github\.com/okkeyapp/okkey-enterprise/\.github/workflows/publish-images\.yml@refs/(?:tags/v[0-9]+\.[0-9]+\.[0-9]+(?:-[0-9A-Za-z-]+(?:\.[0-9A-Za-z-]+)*)?|heads/release/[0-9A-Za-z._-]+|heads/hotfix/[0-9A-Za-z._-]+)$'

for image in \
  ghcr.io/okkeyapp/okkey-enterprise/api \
  ghcr.io/okkeyapp/okkey-enterprise/web \
  ghcr.io/okkeyapp/okkey-enterprise/worker
do
  digest_ref="$(docker image inspect --format '{{index .RepoDigests 0}}' "${image}:${OKKEY_ENTERPRISE_IMAGE_TAG}")"
  cosign verify \
    --certificate-identity-regexp "${identity_regexp}" \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
    "${digest_ref}"
done
```

Заметки к релизу лежат на странице релизов GitHub: [github.com/okkeyapp/okkey/releases](https://github.com/okkeyapp/okkey/releases). У предрелиза в заметках есть отметка, что это ещё не финальная версия.

## Как проверить

```bash
cd ~/okkey
docker compose -p okkey -f docker-compose.prod.yml --env-file .env ps
curl -fsS http://127.0.0.1:4000/health
```

Сервисы `api`, `web` и `worker` запущены, у `api` состояние healthy. В ответе `/health` есть `"status": "ok"`. Откройте веб и войдите. В окне «Обновление системы» текущая версия Okkey совпадает с поставленным релизом.

## Частые ошибки

| Что видно | Что сделать |
| --- | --- |
| `docker compose pull` не находит тег | Тега ещё нет в GHCR. Оставьте прежний `OKKEY_IMAGE_TAG` и прежний файл Compose. |
| `cosign verify failed` | Образ не совпал с подписью. Не запускайте его. Верните прежний тег из копии `.env`. |
| `password authentication failed for user "okkey"` | `POSTGRES_PASSWORD` не от этого тома. Верните `.env` из копии. |
| Установщик пишет, что тег в `.env` не изменён | Так и должно быть, если `.env` уже есть. Тег правьте в файле сами. |
| В `.env` случайно оказался `OKKEY_RESET_VOLUMES=1` | Уберите переменную до `up`. Иначе сотрутся база, Redis и MinIO. |
| Онлайн-строки в окне пустые при `OKKEY_UPDATE_ISOLATED=true` | Используйте [офлайн-пакет](#изолированный-режим) ядра или Compose. |
